# 30. 検証計画（正しさ / 負荷）

棚卸商品管理機能の修正（発注/棚卸の属性分離・自社加工品の登録経路・費目の手動選択・既存データの取り込み）が
「狙った問題を解決できているか」を検証する計画。**(a) 業務的正しさ** と **(b) システム負荷** を分けて定義する。

> ⚠️ 前提：本検証は**モックでは実施できない**（24件・履歴ハードコード・インメモリのため）。
> 実データを載せた**ステージング環境**＋負荷試験環境で行う。モックは概念実証（属性分離の挙動確認）に留める。
> モックで確認できる操作層は [31. モック操作確認](./31_mock_verification.md) を参照。

---

## (a) 業務的正しさの検証 — MUGEN実データ突合

### 検証ゴール
発端の「MUGENで2月のインフォマート数値が合わない」が、本修正で解消すること。
具体的には **棚卸対象から漏れていた商品（発注先を持たない書き起こし商品・中間加工品）が棚卸に計上され、正解値と一致する** こと。

### 仮説（直すべき漏れ）
| 漏れの種類 | 旧UIでの状態 | 期待 |
|---|---|---|
| `route='delivery'`（発注先なし）の書き起こし商品 | 発注メニューに出ず棚卸対象に含められない | 新UIで一覧表示・棚卸ONに取り込める |
| `route='in-house'`（中間加工品） | 登録経路自体が無く未登録 | 新規追加画面で登録でき棚卸対象になる |

### 手順
1. **影響範囲の抽出**：2月時点で「棚卸対象であるべきだが旧UIでは出てこなかった」商品を列挙（下記SQL観点）。
2. **正解値の定義**：インフォマート（および原価/仕入の正解データ）から2月の期待計上額を確定。
3. **取り込み実行**：新UIで対象商品を棚卸ONに（一括「棚卸対象に含める」）＋中間加工品を新規登録。
4. **突合**：棚卸計上額（= Σ 在庫数量 × 棚卸推奨単価）を正解値と比較。
5. **差分分析**：残差があれば原因を分類（後述）。

### 突合の観点（擬似SQL）
```sql
-- ① 旧UIで漏れていた候補（発注先なし or 中間加工品で棚卸OFF）
SELECT route, COUNT(*) AS cnt
FROM products
WHERE store_id = :mugen
  AND inventory_on = false
  AND (route = 'delivery' OR route = 'in-house')
GROUP BY route;

-- ② 取り込み後の棚卸計上額 vs 正解値
SELECT SUM(h.quantity * p.price) AS 棚卸計上額
FROM products p
JOIN inventory_history h ON h.product_id = p.id
WHERE p.store_id = :mugen
  AND p.inventory_on = true
  AND h.period = '2026-02';
-- ↑ をインフォマート由来の期待値と突合
```

### 合否基準
- 棚卸対象商品数：旧UI表示件数 < 新UI表示件数（書き起こし・中間加工分が増える）。
- 棚卸計上額の差異が**許容誤差内**（理想は0円、端数丸めのみ許容）。
- 残差の原因が以下に分類でき、いずれも仕様で説明可能：
  - `price=0`（棚卸推奨単価未設定） / 費目誤り（→ OQ-11） / 税区分 / 単位換算。

## (b) システム負荷の検証

### 対象と計測指標
| 対象 | シナリオ | 主要指標 | 閾値（仮） |
|---|---|---|---|
| **既存71万件の一括更新（案1）** | 「発注OFF/棚卸ON」へ分割バッチ更新（例 1万件/バッチ） | バッチ所要時間 / DBロック / レプリ遅延 / エラー率 | 1万件バッチ < 数秒、レプリ遅延が閾値内、エラー率0% |
| **一覧の取得・描画（OQ-03/04）** | サーバーサイドページング（50件/ページ）で商品1,000 / 10,000件 | API応答 P50/P95、初回描画時間 | P95 < 数百ms |
| **検索フィルタ** | 入力デバウンス200msでの逐次検索 | 検索API P95、無駄リクエスト数 | デバウンスで発火回数が抑制される |
| **一括「棚卸対象に含める」操作** | 現実的上限（全件選択での更新）をユーザー操作で実行 | 応答時間 / タイムアウト有無 | UIがブロックしない（非同期 or 進捗表示） |

### データ準備
- MUGEN規模（インフォマート約39万＝45% / 書き起こし約32万＝37% ＝ 計71万件超）相当のシードデータをステージングに投入。

### 試験方法
- 負荷ツール（k6 / JMeter / locust 等）でAPIエンドポイントを叩く。
- 一括更新は本番想定の実行時間帯・並列度・バッチサイズで実測し、**負荷を分割実行**した場合の安全域を確認（PO/エンジニア合意の「負荷は分けて実行」前提）。

### 案2採用との関係
今回のリリースは**案2（UI先行・一括更新なし）**。よって(b)のうち「71万件一括更新」は**後追いタスク（OQ-12）の事前検証**であり、初回リリースのクリティカルパスではない。
初回リリースで必須なのは「一覧取得・描画」「一括取り込み操作」の応答性であり、ここはサーバーサイドページング（OQ-03）実装が前提条件。

## モックでできること / できないこと

| 項目 | モック | ステージング＋実データ |
|---|---|---|
| 属性分離の挙動（発注OFFでも棚卸ON可 等） | ✅ 概念実証 | ✅ |
| 書き起こし商品が一覧に出る | ✅ UI確認 | ✅ |
| MUGEN数値の一致（(a)） | ❌ | ✅ 必須 |
| 71万件の負荷（(b)） | ❌（全件再描画・インメモリ） | ✅ 必須 |
